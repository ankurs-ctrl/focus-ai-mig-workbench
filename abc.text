Yes — for local OAuth you must configure these in:

`services/sttm-builder/.env.local`

not only `infra/snowflake/env/client.env`.

Add/fill:

```env
AUTH_SESSION_SECRET=<strong-random-string>
AUTH_SESSION_ENCRYPTION_KEY=<fernet-style-or-random-key>
```

Fast way on the client AVD PowerShell:

```powershell
python -c "import secrets; print('AUTH_SESSION_SECRET=' + secrets.token_urlsafe(64))"
python -c "from cryptography.fernet import Fernet; print('AUTH_SESSION_ENCRYPTION_KEY=' + Fernet.generate_key().decode())"
```

If `cryptography` is not available, this is also okay:

```powershell
python -c "import secrets; print('AUTH_SESSION_SECRET=' + secrets.token_urlsafe(64)); print('AUTH_SESSION_ENCRYPTION_KEY=' + secrets.token_urlsafe(48))"
```

Then restart the local backend/frontend completely.

For SPCS/client deployment, you should prefer the Snowflake secret:

```env
SNOWFLAKE_OAUTH_SESSION_SECRET_OBJECT=FFP_HDP_OPS_DB_DEV.SCH_HDP_ADMIN.STTM_BUILDER_OAUTH_SESSION_KEYS
```

In SPCS, the deploy spec maps that Snowflake secret into `AUTH_SESSION_SECRET` and `AUTH_SESSION_ENCRYPTION_KEY`, so you do not need to hardcode those values in code.

One important thing: these values are not your Snowflake password. They are just app-side keys used to sign OAuth state cookies and encrypt the app’s session token storage.
