## 1. Missing source columns and row counts

**I found a separate code gap for row counts—not just the failed column request.**

### Why the target shows columns

The target has its own small metadata request; all **287 sources** are fetched in a separate large batch. The target can therefore succeed independently. Also, a previously populated count is enough to display “37 cols.”

The source request ended with **HTTP 499**, meaning the client disconnected before receiving its response. We have not proved whether this was a timeout or cancellation.

### Why row counts remain blank

When reopening a saved mapping, the frontend initializes table nodes with **blank row counts**. It then fetches columns and relationships, **but does not fetch row counts again**.

See `frontend/src/features/sttm/store/sttm-builder-slice.ts:6932` and `frontend/src/features/sttm/context/sttm-builder-context.tsx:901`.

### Recommended fixes

1. **Restore counts independently:** fetch lightweight catalog row counts and column counts when opening a mapping. Avoid running `COUNT(*)` against every source.
2. **Load columns in smaller batches:** start with approximately 25 tables per request and limited concurrency, then tune using measured timings.
3. **Keep partial successes:** one failed table should not discard metadata for the entire batch.
4. **Use per-table errors and retry:** clear errors after successful retries. Currently a shared error flag can mark every unloaded source “Columns unavailable.”
5. **Add request timings and query IDs:** distinguish slow Snowflake queries, client timeouts, and navigation cancellations.

These are recommendations; **I haven’t implemented them**. Generating missing semantic YAML will not repair these metadata-loading issues.
