## 1. Project creation times out while initializing target mappings

### Reproduction

In **New Project**:
1. Select **CRM Migration**.
2. Select **Create target mappings automatically**.
3. Select all ten approved target tables.
4. Click **Create Project**.

The UI reports:

```text
Request failed with status code 504
```

The endpoint is:

```text
POST /api/v1/projects/from-template
```

The backend can continue processing and save the project after the client-facing connection closes.

### Verified incident evidence

Two ACTIVE projects named `Kovitz_3` were found:

```text
Project IDs: 1001 and 1002
```

Each eventually contained:
- Ten distinct draft target mappings.
- 242 target-attribute rows.
- Populated snapshots and valid latest-snapshot references.

At the first two logged disconnects, the corresponding project had **9/10 committed mappings**. The last mapping was saved afterward.

Nginx recorded **499**, while the screenshot showed **504**. The precise component issuing the 504 remains unverified; do not assume nginx’s default timeout caused it.

### Main performance issue

The implementation creates the ten mappings **serially**, and each mapping goes through the normal full autosave workflow:

```text
Create project
→ Create mapping header
→ Read mapping
→ Run full autosave
→ Save snapshot and target attributes
→ Update draft and metadata
→ Read mapping and recalculate counts
→ Repeat for next target
```

For a blank target-only mapping, this performs unnecessary prior-state reads, empty deletes, repeated updates and count calculations.

Observed database-session evidence:

| Correlated project | Relevant metadata queries | Operation span | Sum of SQL elapsed time |
|---|---:|---:|---:|
| 1001 | 134 | 75.1 seconds | 56.2 seconds |
| 1002 | 134 | 95.9 seconds | 75.0 seconds |

For the slower session, approximately:
- 40 seconds were SQL compilation.
- 29 seconds were execution.
- 6 seconds were transaction blocking.

These are database metrics, **not exact HTTP request durations**.

Compilation here means Snowflake planning the application’s metadata `INSERT`, `UPDATE`, `SELECT` and related statements—not generating or validating source-to-target transformation SQL.

**No Auto-map inference runs in this blank project-bootstrap path.**

### Specific implementation problems

**A. Full autosave is reused for initial creation**

New mappings are treated like existing edited mappings, causing unnecessary persistence work.

Relevant locations:
```text
services/sttm-builder/app/core/project_service.py:1227
services/sttm-builder/app/core/project_service.py:1715
services/sttm-builder/app/core/project_service.py:2245
```

**B. Global mapping counts are repeatedly recalculated**

`get_sttm_record()` invokes `_mapping_counts_by_sttm()`, which aggregates counts across mappings instead of retrieving only the newly created mapping’s count. This happens repeatedly during the ten-target loop.

```text
services/sttm-builder/app/core/project_service.py:2105
services/sttm-builder/app/core/project_service.py:3157
```

**C. Transaction ownership is broken**

The outer bootstrap starts a transaction, but nested autosave also starts and commits a transaction on the **same session**.

The inner commit can commit the project and earlier mappings before the entire bootstrap finishes. A later outer rollback cannot undo those already committed changes.

```text
services/sttm-builder/app/core/project_service.py:1110
services/sttm-builder/app/core/project_service.py:2160
```

**D. Completion is marked too early**

Project metadata is assigned:

```text
bootstrap_status="COMPLETE"
```

before the mapping-creation loop has completed.

```text
services/sttm-builder/app/core/project_service.py:1194
```

**E. Retry handling is not sufficiently safe**

The existing idempotency logic:
- Searches for a matching key.
- Skips existing logical target mappings.
- Does not fully verify that each existing shell has completed attributes and snapshots.
- Does not provide a concurrency-safe creation claim.

Closing/reopening the modal generates a new key. A timeout followed by a new attempt can therefore create another project while the original request is still completing.

```text
frontend/src/features/projects/new-project-modal.tsx:116
services/sttm-builder/app/core/project_service.py:1177
```

**F. Cache behavior can hide completed work**

Frontend summary invalidation runs only after a successful response. A timeout can leave an old project list visible even though the project was committed. Backend invalidation occurs before creation, allowing concurrent reads to repopulate stale summaries.

### Required fix direction

- Implement a **bootstrap-specific bulk initialization path** for mapping headers, target attributes and snapshots.
- Build the blank mapping payloads in memory before writing.
- Avoid full autosave, empty deletes and prior-snapshot reads for new mappings.
- Calculate counts once.
- Give the operation **one transaction owner**.
- Mark bootstrap complete only after all required children are persisted.
- Make retries concurrency-safe and completeness-aware.
- Invalidate caches after commit.
- If processing remains long-running, return a durable operation ID and progress status instead of holding the HTTP request.

**Do not simply parallelize the current loop on the shared session.** That risks transaction interference. Reduce and batch the database work first.

### Timeout investigation still needed

The inspected configuration has:
- Frontend template-create timeout: **300 seconds**.
- Nginx `/api/` read/send timeouts: **3,600 seconds**.

Therefore, raising those values without identifying the actual 504 responder is not an evidence-based fix. Add request correlation and timing across ingress, nginx and backend.

### Acceptance tests

- Ten targets create exactly ten mappings with correct initial attributes and snapshots.
- No model calls or source-data reads occur.
- Query count is substantially reduced and measured.
- A mid-operation failure follows the chosen atomicity/recovery contract.
- Concurrent retries with the same key do not duplicate projects or mappings.
- A disconnected client can recover the final result without creating a second project.
- An incomplete existing shell is repaired or explicitly reported—not silently skipped.
- The project list reflects committed completion.

**Do not automatically delete projects 1001 or 1002.** One associated mapping already has later edits.

## 2. AI Recommendations tab is hidden in the main Join Definitions dialog

### Observed behavior

In:

```text
Source Selection → Join Definitions
```

the **AI Recommendations** tab is hidden.

The tab implementation still exists. It is not removed globally, and it remains available in the CTE/derived-source editor.

### Exact cause

The main relationship-flow component passes:

```tsx
showRecommendations={Boolean(tables || onJoinsChange)}
```

Location:

```text
frontend/src/features/sttm/source-target/table-relationship-flow.tsx:1266
```

The main Source Selection page mounts the component without either prop:

```tsx
<SttmTableRelationshipFlow />
```

Therefore:

```text
tables = undefined
onJoinsChange = undefined
showRecommendations = false
```

The modal conditionally omits the tab.

Relevant locations:

```text
frontend/src/app/sttm/builder/new/page.tsx:44
frontend/src/features/sttm/source-target/join-definitions-modal.tsx:714
```

**This is not caused by empty recommendations.** When enabled, the tab has an empty-state display.

### When it was introduced

Commit:

```text
3ccecacddfe3857b0fc2efaaf0ee44bead5f0677
Apply Auto-map v3 and inline candidate review fixes
```

Date: **November 5, 2026**

That push’s deployment failed. The change was included in the subsequent successful UAT deployment of `fce9e7e`:

[UAT run 42041987548](https://github.com/FocusFP/ffp_ai_mig_workbench/actions/runs/42041987548)

It was **not introduced by the November 11 overlay or the durable-v2 fixes**.

### Required fix direction

- Enable AI Recommendations explicitly for the main Source Selection dialog.
- Do not infer feature visibility from whether `tables` or `onJoinsChange` were supplied.
- Preserve CTE-editor behavior.
- Verify recommendation loading, review and application work correctly in the main context.
- Keep suggested joins separate from accepted joins; do not automatically modify the graph.
- Preserve existing manual joins and row-level “Review suggested join” navigation.

### Acceptance tests

- Main Join Definitions shows:
  - Driving Joins
  - Additional Joins
  - AI Recommendations
- Empty recommendations display an empty state rather than hiding the tab.
- Loading and retrieval failures have visible states.
- Reviewing a suggestion does not apply it.
- Explicit acceptance adds the intended join once without overwriting manual joins.
- CTE-editor recommendations continue working.
- Existing row-level join-review navigation still works.

**Scope:** fix these two workflows without changing Auto-map inference, FIR eligibility, durable-v2 capacity, or unrelated mapping behavior.
