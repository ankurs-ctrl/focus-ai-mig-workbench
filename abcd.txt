# A. Auto-map code fixes

## 1. Reconcile checkpoints with successful worker results

**File:** `services/sttm-builder/app/core/automap_native_delivery.py:147–161`

**Current defect:** Any cached checkpoint overrides the worker response. An older `1/2` checkpoint replaces a successful `2/2` result.

**Code correction:**
- Reconcile results per target.
- Preserve compatible validated checkpoints when worker delivery fails.
- Include newer validated worker results when delivery succeeds.
- Check job, generation, target, and input revision before merging.
- Do not silently overwrite conflicting same-revision results.

**Required regression:** Checkpoint `1/2` → worker success `2/2` → final result must contain `2/2`.

## 2. Preserve completed checkpoints when the parent deadline expires

**File:** `services/sttm-builder/app/core/auto_mapping_proxy.py:1967–1998`

**Current defect:** A recovered mapping can reach the progress callback before the deadline, then be discarded during terminal assembly.

**Code correction:**
- Distinguish **new late results** from **finalizing already-accepted results**.
- Preserve eligible checkpoints at the deadline.
- Mark only unfinished targets as `not_completed` or equivalent.
- Keep generation/revision fencing and rejection of genuinely late writes.

**Required regression:** A mapping recovered before the deadline remains mapped in the terminal partial result; a new result arriving after cutoff cannot overwrite it.

**Do not remove the deadline guard globally.**

---

## 3. Correct native response completion classification

**File:** `services/sttm-builder/app/core/automap_native_transport.py:79–95`

**Current defect:** Missing status can be treated as completed. Invalid native tool content then raises a terminal exception, causing an uncertain call’s permit to be released.

**Code correction:**
- Separate **remote completion classification** from **content validation**.
- Establish completion using the supported provider response contract.
- Treat malformed/nonterminal/uncertain responses as uncertain, not automatically terminal.
- Keep uncertain calls protected until reconciliation.
- Do not replay ambiguous POSTs automatically.

**Required regressions:** Statusless/unpaired tool response, explicit nonterminal response, truncated response, confirmed terminal failure, and confirmed terminal success with invalid content. Assert permit state as well as returned errors.

---

## 4. Validate Analyst completion before releasing its permit

**File:** `services/sttm-builder/app/core/automap_native_ports.py:632–656`

**Current defect:** The code sets `terminal=True` and calls `pool.finish()` before checking the response envelope. An `in_progress` response releases capacity prematurely.

**Code correction:**
- Classify remote completion before deciding whether to release the permit.
- Keep uncertain/nonterminal outcomes protected.
- Perform SQL/content validation separately after completion classification.
- Avoid requiring fields that the supported Analyst contract does not provide.

**Required regression:** `in_progress` must not free the permit; a confirmed completed response containing invalid SQL should fail validation without being misclassified as a still-running call.

# B. SQL-upload code fixes

## 5. Support multiple relation instances of the same physical table

**Files:**
- `frontend/src/features/sttm/mapping/sql-upload-workspace.ts:114`
- `frontend/src/features/sttm/mapping/mapping-utils.ts:100–105`
- Backend scope contract: `services/sttm-builder/app/core/query_scope_contract.py:155–190`

**Current defect:** The backend preserves separate aliases, but the editable graph uses physical-table identity and cannot represent:

```sql
COUNTRY_CODES ccMail
COUNTRY_CODES ccOther
STATE_CODES scMail
STATE_CODES scOther
```

That causes your Apply Preview error.

**Code correction:**
- Keep physical-table identity separate from query-scoped relation-instance identity.
- Use instance IDs for graph nodes, joins, source bindings, and expression references.
- Carry those identities through Apply, save, reopen, compilation, and Auto-map.
- Preserve original aliases, predicates, CTE boundaries, and population logic.

**Required regression:** Upload the exact Contacts file and preserve both country joins and both state joins through Apply → save → reopen → compile.

**Do not fix this by removing the guard or deduplicating the joins.**

## 6. Make catalog verification resumable instead of repeatedly checking the first eight sources

**Files:**
- `services/sttm-builder/app/core/upload_reference_status.py:14–47`
- `services/sttm-builder/app/routers/upload.py:418–454`
- `services/sttm-builder/app/routers/upload.py:595–624`

**Current defect:** The shared eight-call budget cannot verify eleven sources plus semantics. Background processing restarts the same pass, leaving later sources unchecked.

**Code correction:**
- Retain completed checks.

- Use bounded bulk metadata retrieval where appropriate.
- Separate catalog existence from semantic availability.
- Return explicit pending/failed verification states; never convert exhaustion into missing.
- Ensure background readiness reflects required verification, not merely the existence of stored reference rows.

**Required regression:** With all eleven Contacts sources available, every source eventually becomes verified. One slow source must not starve the rest.

**Simply increasing the limit from eight to eleven is not a general fix.**

## 7. Remove excessive sequential learning preparation from the foreground upload request

**Files:**
- `services/sttm-builder/app/routers/upload.py:978–1028`
- `services/sttm-builder/app/core/target_mapping_patterns.py:1032`

**Current defect:** The upload waits for pattern persistence and learning-work-item creation before returning. The fresh test performed **53 work-item MERGEs**, consuming approximately **31.6 seconds** of SQL time.

A historical work-item MERGE also spent **59.7 seconds transaction-blocked** before timing out.

**Code correction:**
- Batch metadata writes instead of executing one MERGE per work item where practical.
- Keep foreground transactions short.
- Durably accept the upload and record pending work before returning.
- Move lengthy learning preparation to recoverable background processing.
- Avoid concurrent duplicate processing of the same logical upload.
- Add correlated phase timings to distinguish connection, persistence, lock wait, commit, and response time.

**Required regressions:** Single upload, concurrent same-file uploads, background failure, and restart after durable acceptance. Verify no queued work is lost.

**Do not solve this only by increasing timeouts.**
