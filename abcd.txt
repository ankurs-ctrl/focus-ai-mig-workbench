## 3. The `209.0` versus `209` hash issue

### Observed failure

The first durable-v2 job failed with:

```text
_FastInvariantError: prepared_hash_mismatch
Fast Auto-map requires the frozen prepared proxy handoff
```

Job:

```text
39d5074e-6aec-5f4e-9357-c11371cf367a
```

It failed while reconstructing and validating pending batches.

### Why numeric representation matters

The preparation hash uses JSON serialization. These values are numerically equal but serialize differently:

```json
{"duration_ms":209.0}
```

```json
{"duration_ms":209}
```

Consequently, their hashes differ.

The hash includes learning-context diagnostics. Some of those dictionaries contain untyped values, so model validation does not necessarily restore an integer to a float.

In Snowsight, I verified that:

```text
PARSE_JSON({"x":209.0}) → stored INTEGER 209
```

The failed job contained:

```text
project_context.duration_ms = 209        INTEGER
correction_history.duration_ms = 489.3  DECIMAL
```

An offline test using the actual restoration and pending-request functions reproduced the exact failure by changing only `12.0` to `12`.

**Important qualification:** this proves the defect mechanism. We did not retain enough original pre-storage evidence to prove that `209.0 → 209` was the sole change responsible for that particular live job.

### My fix

I did **not**:
- Disable hash validation.
- Recompute hashes on load to make corrupted records pass.
- Convert arbitrary integers back into guessed floats.

Instead, persistence now stores an additional versioned exact-JSON representation of the hash-bearing sections:

```text
request_envelope
partial_responses
response
```

The marker is:

```text
_automap_exact_json
encoding: automap-exact-json-v1
```

The existing SQL-visible fields remain available for operational queries. On load, the decoder restores the exact JSON sections before model validation.

It checks:
- Encoding/version and expected structure.
- Duplicate keys.
- Non-finite numbers.
- Consistency with the SQL-visible projection.

Mutable job status, ownership and lease fields are not overwritten from the exact-JSON supplement.

I also updated the **background restart path**, because fixing only browser-triggered loading would leave restart recovery vulnerable.

**Legacy records still use the original validation. Already-damaged old jobs are not silently repaired.**

## 4. The `'str' object has no attribute 'get'` issue

### Observed failure

The next fresh run failed all ten batches with:

```text
'str' object has no attribute 'get'
```

Job:

```text
19269947-4863-5660-bc3b-5b0106e97392
```

### Exact cause

The real worker response contains:

```python
response.meta["auto_map_fast_path"] == "v1"
```

That field is a **selector string**.

The durable retry code mistakenly treated it as a dictionary:

```python
(response.meta.get("auto_map_fast_path") or {}).get("fast_diagnostics")
```

The actual diagnostics are here:

```python
response.meta["auto_map_retrieval"]["auto_map_fast_path"]["fast_diagnostics"]
```

I reproduced the exception through actual worker-response construction, HTTP serialization, proxy parsing and completion logic. It occurred even with successful model output—not only malformed responses.

### My fix

I corrected both diagnostics reads:
- The initial response.
- The replacement response after a retry.

A shared helper now reads the canonical nested structure:
- Missing/null optional diagnostics are handled.
- Malformed diagnostic objects produce an explicit contract error.
- The `"v1"` selector is not treated as diagnostics.

The old retry test used an artificial root-level dictionary, which concealed the problem. I replaced that assumption with real worker-response shapes in regression tests.

### Root cause: producer and consumer disagree

The normal publication snapshot includes physical column names and types, but does **not** consistently include physical-table grain—the meaning of one row and relevant uniqueness assumptions.

The FIR matcher then requires known, compatible grain **even when the source columns match exactly**.

```text

→ Matcher requires positive grain evidence
→ Recipe becomes unresolved
```

Relevant code:

- Compatibility checks: `services/sttm-builder/app/core/target_mapping_patterns.py:2146`

I reproduced this with the actual constructor and matcher:
- Missing historical grain → unresolved.
- Explicit matching contracts on both sides → exact precedent accepted.

**We should fix the missing contract, not invent grain or bypass the check.** The published mapping also used a filtered `cte_hh_src` population that the current graph does not contain; matching column names alone does not prove equivalent population behavior.

## 4. OWNERNAME: the actual published rule was NULL—not full-name concatenation

This was an important finding.

The exact published version contains:

```sql

```

Its mapping row records:

```text

constant_value: "NULL"
```

The FIR extractor explicitly treats SQL `NULL` as a literal, then records:

```text

has_project_specific_literal: true
expression: null
scope: project
```

It attaches:

```text
Do not reuse the project-specific literal.
```

The recipe does not preserve the constant as an executable value.

Because the recipe belongs to project 301, the strict project-scoped lookup excludes it for project 501. A broader retrieval path reintroduces it as guidance, explaining why it can appear with an empty applicability-exclusion list while remaining unresolved.

### Root cause

There are two things to distinguish:
- **Intentional policy:** do not blindly copy project-specific constants.
- **Lossy representation:** the FIR recipe no longer clearly distinguishes intentional SQL NULL from an unavailable/redacted expression.

Code: `services/sttm-builder/app/core/target_mapping_patterns.py:373`

**I cannot justify copying NULL into the current mapping without confirming the intended business behavior.** Likewise, the full-name draft produced by Auto-map is not evidence that the traced published OWNERNAME rule required concatenation.

## 5. Why published SQL alone does not repair these gaps

The publication flow stores the full SQL and parsed model. But the FIR target-pattern projection primarily consumes **snapshot mapping rows and their attached metadata**.

It does not generally reconstruct complete per-source contracts and lineage from the stored SQL.

That creates this gap:

```text
Correct published SQL exists
→ Mapping-row projection is incomplete
→ FIR recipe lacks required compatibility metadata
→ Retrieval retains it as guidance
→ Primary source decision remains unresolved
```

The enrichment path adds explanatory text and applicability conditions, but does not reliably fill missing type/grain contracts.

Some tests missed this because their positive fixtures manually supplied grain. They did not exercise the ordinary frontend snapshot that omits it.

## What should be fixed

1. **Preserve explicit per-source contracts and lineage through publication.** Reuse verified metadata; leave genuinely unknown grain unresolved.
2. **Make project/CRM eligibility explicit and explainable.** Distinguish scope rejection from missing compatibility.
3. **Reconcile proven logical-to-physical lineage**, preserving CTE population semantics.
4. **Represent SQL NULL distinctly from redacted project literals.**
5. **Repair the source-to-transformation handoff** for safely bound candidates awaiting an expression.
6. **Stop presenting invalid drafts as completed mappings**, and fix the placeholder-based coverage count.

**Conclusion:** the knowledge was largely captured, but layered metadata, eligibility and handoff problems prevented its safe reuse. Some restrictions are legitimate; the code currently does not explain them well enough and sometimes loses information needed to satisfy them.
