# Investigate and correct the Auto-map context-batching implementation

## Objective

We are developing a Snowflake-based AI Migration Workbench that imports SQL, builds source-to-target mappings, and uses Cortex Agents for Auto-map.

We implemented parallel, whole-table context batching to address growing model context and oversized requests. The implementation is deployed to UAT and the services are healthy, but a real UAT Auto-map request fails during preparation, before any scan agents run.

Please investigate the implementation using the history and evidence below. We need a permanent correction—not a higher limit, arbitrary context truncation, bypassed validation, or another unverified hotfix.

Clearly distinguish:
- What was originally wrong.
- What the proposed architecture was intended to solve.
- What is implemented.
- What has actually passed testing.
- What is failing now.
- What is measured versus inferred.
- What changes are needed without violating the original requirements.

## 1. Original issue

Auto-map accumulated substantial context from several sources:

- Source and target semantic models.
- Column descriptions and table-level rules.
- Uploaded SQL and derived-source definitions.
- CTEs, joins, transformations, and lineage.
- Existing mapping rows.
- Learning records, precedents, and execution context.
- Workspace state and previous results.

The concern was that too much evidence was being carried into model requests. Larger mappings could exceed context/message budgets, and one large table could prevent unrelated mapping work.

We also needed to preserve correct mappings already obtained. Optional evidence retrieval failures or incomplete evidence should not erase validated results.

We did not want to solve this by deleting meaningful information, clipping semantic models, or asking the model to guess.

Do not invent a single exact historical provider error for every earlier failure. The central issue was growing context and oversized messages; the precisely measured current error is documented below.

## 2. The idea we decided to implement

The user proposed a staged, distributed approach:

1. Keep the full original evidence in the backend.
2. Divide semantic evidence into independent table-level batches.
3. Send batches to separate scan-agent calls, in parallel where capacity allows.
4. Collect provisional source candidates.
5. Retain those candidates and their evidence references.
6. Reduce and compare candidates across batches.
7. Retrieve additional evidence through stable handles or Search when necessary.
8. Perform the final mapping using bounded, relevant evidence.

The user specifically clarified:

> Never split one table’s semantic bundle across scan batches.

“Drop context” meant:

> Stop repeating it in subsequent model messages—not delete the original backend evidence.

The intended outcome was that one genuinely oversized table would not fail all independent work. The application should continue where justified and clearly identify incomplete coverage.

## 3. Non-negotiable requirements

Preserve these requirements in any correction:

- Keep each table’s semantic evidence together.
- Retain the exact original backend context.
- Preserve table-level population rules, join constraints, grain, and relevant lineage.
- Preserve distinct relation instances, including self-joins.
- Preserve user-authored SQL, constants, project values, transformations, and existing mappings.
- Never invent source candidates, variable values, or mappings.
- Never describe incomplete evidence as an exhaustive no-match.
- Surface partial coverage to the user.
- Keep validated results when optional reads fail.
- Use bounded requests and bounded concurrency.
- Do not share a Snowpark session concurrently across independent operations.
- Do not recycle uncertain remote-call permits simply because a timeout elapsed.
- Do not silently bypass safety checks.
- Do not split a table merely to make the request fit.
- Do not confuse healthy infrastructure with successful application acceptance.

## 4. What we implemented

### A. Immutable context and whole-table groups

Implemented context snapshots, stable record identities, scoped retrieval handles, and table-level atomic groups.

Oversized table groups can be excluded with explicit partial-coverage information while retaining their original evidence.

### B. Parallel scanning

- Explicit coverage for failed, timed-out, and unsubmitted work.
- Cancellation handling.
- No late mutation of completed results.
- Shared admission controls.

Relevant modules:

- `automap_scan.py`
- `automap_parallel.py`

### C. Candidate reduction and evidence retention

Implemented bounded reduction with:

- Durable archives.
- Provisional candidate retention.
- Stable deduplication.
- Pinned candidates.
- Complementary-role requirements.
- Reversible pruning.
- Partial-coverage semantics.

Relevant module:

- `automap_reduce.py`

### D. Admission and transport safeguards

Implemented a fixed Snowflake permit inventory with states:

```text
FREE → HELD → FREE
            ↘ QUARANTINED
```

The implementation uses ownership, epochs, fences, conditional updates, and commit acknowledgment.

Transport safeguards include bounded responses, single-attempt dispatch, and durable thread references.

Relevant modules:

- `automap_admission.py`
- `automap_scan_transport.py`

Important limitation:

**The shared permits cap scan/reduction calls, not every final mapping or transformation call.**

- Only 11 workspace rows match exactly.
- Those 11 have empty source references.
- Case-normalized comparison finds 37 matches, including 21 with source references.

As a result, the retained request produces empty dependency sets and falls back to balancing targets rather than exploiting their shared sources.

Reference:

This is not the primary cause of the current overflow, but it weakens the intended batching design.

## 18. Expected permanent correction

Investigate and design the correction around these principles:

1. Include target-table semantics once per message.
2. Include each source-table capsule once per whole-table batch.
3. Let column records reference the capsule included in that same bounded message.
4. Preserve complete evidence when retrieving individual members; references must never silently omit required rules.
5. Represent identical SQL once in the model-facing payload while retaining all originals in backend state.
6. Scope mapping rows to target dependencies while retaining true global constraints.
7. Correct identifier-aware dependency grouping.
8. Use the same serialization and budget accounting in host preflight and runtime.
9. Persist preparation state or safe diagnostic manifests before planning can fail.
10. Return structured size/coverage errors rather than only a generic job failure.
11. Continue to exclude genuinely oversized whole-table groups with honest partial coverage.
12. Add realistic regression tests and repeat actual UAT acceptance before claiming success.

Do not solve this by:
- Raising the limit alone.
- Arbitrarily truncating semantics.
- Deleting original context.
- Splitting a table’s evidence across scan batches.
- Returning fabricated mappings.
- Adding workers.
- Treating green unit tests or READY containers as complete acceptance.
