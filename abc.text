Why datga layer is sqlite and not snwoflake itself?

Because that API isn't standing in for Snowflake — it's standing in for Schwab/Fidelity/Orion, which are genuinely different systems in real life, not Snowflake tables. That distinction is actually load-bearing for the demo, for three reasons:

1. It's what makes the "two paths" story true, not just decorative.
The whole point Vivek wants to prove is: "one path (Snowflake) is a direct semantic-layer read; the other path (iPaaS) has to hop out to real external systems, and that's why it's slower." If the iPaaS path's "external system" is secretly also just a Snowflake table, you're not actually demonstrating two different architectures — you're demonstrating one data source with two labels on it. Someone technical in the room (sounds like Chris's team will have people like that) could reasonably ask "wait, isn't that also just Snowflake?"

2. Snowflake isn't built for the workload this API needs.
The Account/Household API needs cheap, fast, repeated point writes (create household → get → put update, with real retries) — classic OLTP behavior. Snowflake is an analytics warehouse: it's excellent at the semantic-layer read side, but a warehouse can have cold-start/spin-up latency on the first query and isn't designed for many small transactional writes. That's exactly the kind of variance that would sneak into your "8 seconds happy path, 45 seconds with retries" numbers and make them look staged rather than real — the opposite of what you want.

3. It matches what's actually true in production.
In the real system, Orion and Schwab/Fidelity are not Snowflake — they're the actual custodian/wealth platforms. Snowflake only enters the picture as the analytics/semantic layer on top. SQLite here isn't a shortcut so much as it's playing the role of "some other system's database," which is architecturally honest to what iPaaS actually talks to.

That said — if you'd rather run one piece of infrastructure instead of two for the demo, that's a legitimate call too. You'd lose the clean separation above, but you could put the account/household tables in a separate Snowflake schema from the semantic-model data (not the same tables), and have the mock API hit that schema via plain SQL instead of SQLite. It'd still work for Thursday, just with slightly less crisp storytelling and a bit more latency variance to manage.
