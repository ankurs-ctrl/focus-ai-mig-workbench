### New defect: block-review contract conflicts with actual agent responses

The actual agent returned its normal envelope:

```json
{
  "contract_version": "1.0",
  "request_id": "...",
  "operation": "sttm.auto_map",
  "data": {
    "intent": "AUTO_MAP",
    "status": "completed",
    "agent": "AGT_SOURCE_MAPPING",
    "result": {"mappings": {}}
  },
  "meta": {"evidence_review": {}},
  "warnings": [],
  "error": null
}
```

But `automap_evidence_blocks.py:192–204` rejects normal fields such as `contract_version`, `request_id`, `operation`, and `warnings`. It also requires a **root-level** `agent`, whereas the actual responses placed it under `data`.

Seven responses used the normal JSON envelope; one correction returned prose instead.

**Required fix:** reconcile the block-review protocol with the actual agent contract. Normalize only explicitly supported envelope forms, while retaining strict checks for conflicting results, delegation, failure status, block identity, and literal quotes. Do not simply remove the allowlist.

### Additional evidence-context concern

The reviewed block contained approximately **77,748 characters of column-elimination information from key profiling**. One response interpreted uniqueness/null-related elimination as making columns unsuitable for mapping.

The block packet lacked an explicit semantic path explaining what that elimination meant.

**Required improvement:** retain typed ownership and purpose—for example, “eliminated as a primary-key candidate,” not “unavailable for mapping.” Review why this block must gate every target before any mapping decision.

Some responses also contained extra fact fields or nonliteral observations. Envelope compatibility alone may therefore not resolve every review failure.

The backend labels reevaluation `pending`. The frontend interprets that as `definitionPreserved=false`, then settles the original mapped row as `UNMAPPED`.

Relevant locations:


An independent production-reducer probe reproduced this sequence.

**Required fix:** keep the existing definition’s status separate from the replacement proposal’s pending status. Requesting reevaluation must not invalidate a previously mapped definition by itself.
