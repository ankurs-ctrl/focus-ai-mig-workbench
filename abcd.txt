Names such as `ReadAutoMapContext`, `SearchMappingEvidence`, and `ReadMappingEvidence` are therefore instructions for returning JSON to the application—not native registered tools.

### How our client calls them

Source mapping and transformation use stored-agent endpoints:

```text
POST /api/v2/databases/<DB>/schemas/SCH_STTM_METADATA/agents/<AGENT>:run
```

For fast Auto-map:

- `stream: false`.
- A fresh recovery thread is created for each operation.
- Every model call uses `parent_message_id: 0`.
- Later rounds do **not** continue from the previous assistant message.
- Evidence requests are processed by the backend, which builds another request.

**Most consequential compatibility finding:** the fast transport rejects native `tool_use` and `tool_result` response blocks.

Consequently, **adding tools to the agent specification alone is not a safe implementation**. The client must first support the resulting responses and recovery semantics.

### Limits and rights

**Do not combine these different limits:**

- Deployed orchestration budgets: **200/75 seconds**.
- Current documented synchronous Agent REST request timeout: **15 minutes**.
- Documented background request timeout: **6 hours**, requiring threads; our callers do not enable it.
- Tool query execution has a separate `execution_environment.query_timeout`.
- Our fast transport has a **120,000-byte response cap**.
- I could not verify a universal native custom-tool response-size ceiling or maximum execution timeout.

For procedure tools:

- Agent ownership does not automatically confer its owner’s rights on every tool.

Existing `SP_SUBAGT_SOURCE_MAPPING` and `SP_SUBAGT_TRANSFORMATION_RULE` wrappers are `EXECUTE AS CALLER`, but they are not registered tools on these agents and were not found in the inspected application call path.

## Implications for the proposed plan

The phase order is reasonable, with these corrections:

1. **Keep Phase 1 and Phase 2 independent of native-agent changes.** The evidence retention, stale feedback, target identity, and result-delivery problems are already established.

2. **Checkpoint validated target results—not raw model responses.** Include tenant/project authorization, run generation, input revision, and fencing. The UI should consume an authorized backend API, not directly query the checkpoint table.

3. **Do not treat checkpoints alone as the delivery-gap diagnosis.** Add correlated timestamps around worker response construction/send and parent body receipt/parse/validation. Those are the missing observations.

4. **Delta context needs retained conversational state or a compact self-contained context.** Today every call starts at thread root. Simply omitting previously sent evidence would make it unavailable to the next call.

5. **Native-tool prove-out is technically justified, but transport compatibility is a prerequisite.** The current client rejects the very tool blocks the proposed architecture would produce.

6. **Do not benchmark accuracy against `MAPPED` status alone.** Start with candidate reference mappings, obtain business sign-off, then evaluate semantic correctness and preservation separately from compiler acceptance.

The remaining user-only decisions are the **business approver/gold set, client deadline and acceptance thresholds, authorized DEV environment, and provider policy**. Everything above is investigation evidence—not authorization or a claim that the fixes have been implemented.
