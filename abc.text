What is cached in the browser
Data	Browser location	Persistence
Current mapping workspace	localStorage	No fixed expiry; survives refresh, tab close and browser restart

Agent chat history	localStorage	Up to 30 chat sessions; workspace snapshot keeps the latest 12 messages
UI preferences	localStorage	No fixed expiry
Table columns and relationship metadata	In-memory cache	10 minutes
Semantic bundle response	In-memory cache	10 minutes

Project list/summary	sessionStorage	30 seconds

Uploaded SQL handoff	sessionStorage	One-time; removed after the mapping page consumes it

If browser storage becomes too large, the app deliberately removes reloadable content first:
Database catalog trees
Full semantic evidence
Preview rows
Large SQL strings
Large derived-source SQL
It retains the important selections, mapping rows, identifiers and backend snapshot pointers.

After a full browser refresh:
The app first restores the scoped workspace from localStorage.
For an existing mapping, it can restore the authoritative workspace from the backend snapshot.
If browser storage had to use its compact fallback, the catalog may reload, but selected tables and mappings should still be restored.
After more than 5–10 minutes, the application may refresh metadata in the background to avoid showing stale Snowflake schemas. That refresh should not remove the selected tables or mapping work.
So the short answer is: normal back navigation should be immediate and should not require reloading the sidebar hierarchy. Browser caching provides speed; Snowflake autosave provides recovery and durability.
