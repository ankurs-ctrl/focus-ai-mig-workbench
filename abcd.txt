**The ZIP moves in the right direction—smaller selectable-source contracts, CTE output validation, and handling `suggested_queries`—but I would not deploy it unchanged.** It introduces several reproduced regressions and restores transformation-agent calls without the safeguards used by the fast path.

Below I separate **confirmed defects** from **remaining verification gaps**. Nothing has been pushed or deployed.

All code references below are relative to the extracted `_uat_grounded` worktree.

## 1. Valid uploaded CTEs are rejected

**Severity: deployment blocker. Confirmed by existing Ft. Pitt regression tests.**

**Location:** `services/sttm-builder/app/core/automap_fast_context.py:100–105`

The new CTE hydration logic recognizes a wrapper using a regular expression that essentially permits:

```text
SELECT * FROM CTE_NAME
```

But the existing upload/frontend workflow produces self-contained definitions containing:

```text
WITH CTE_NAME AS (...)
SELECT * FROM CTE_NAME
```

The ZIP compares that complete definition against the extracted inner CTE body. Those structures differ, even when they represent the correct uploaded CTE.

**Impact:** Valid Ft. Pitt uploads fail before inference. This also breaks a previously working authored-definition preservation path.

**Recommended change:**

- Use the existing SQL parser and scope/binding machinery, not a regular expression, to recognize supported wrappers.
- Resolve the selected CTE within its actual SQL scope.
- Compare the corresponding normalized definition and dependencies, not the wrapper against the inner body.
- Preserve the original uploaded SQL separately.
- Reject genuinely different definitions rather than simply bypassing the comparison.

**Required test:** The real upload → frontend snapshot → backend request fixture must pass unchanged, including all four Ft. Pitt CTEs.

## 2. The dependency hash does not establish that the current SQL is unchanged

**Severity: deployment blocker. Confirmed by an offline mutation probe.**

**Location:** `services/sttm-builder/app/core/automap_fast_context.py:98–106`

The code calculates an expected hash from the authored definition. However, if a node already carries that matching hash, it skips comparing the node’s actual SQL against the expected body.

The reproduced sequence was:

1. Hydrate a valid CTE.
2. Change its SQL while retaining the previous hash.
3. Submit it again.
4. The changed definition is accepted.

For example, adding a filter that removes all rows was accepted by the offline path.

**Impact:** A stored hash can mask changed filters, population, or transformation logic. SQL compilation alone cannot prove that an executable query still matches the authored definition.

**Recommended change:**

- Recompute the identity from the **actual current definition**, not merely the expected definition.
- Verify its relationship to the authored SQL independently.
- Treat incoming hashes as identifiers to check—not proof.
- Bind the validation result to the current SQL, exposed outputs, relevant dependencies, and graph revision.
- Invalidate the proof when any of those inputs change.

**Required test:** Changing a filter, expression, parent reference, or output while retaining an old hash must invalidate the contract.

## 3. Parent CTE renaming breaks qualified references

**Severity: functional blocker for affected dependent CTEs. Reproduced offline.**

**Location:** `services/sttm-builder/app/core/automap_fast_context.py:91–96`

The code renames a table reference without updating its implicit column qualifier.

The probe produced:

```text
Before: SELECT p.X47 FROM p
After:  SELECT p.X47 FROM dp
```

The column still refers to `p`, but the relation is now named `dp`.

**Impact:** Valid dependent CTEs become invalid SQL after hydration.

**Recommended change:**

- Reuse scope-aware alias/binding utilities.
- Preserve the original relation qualifier through an explicit alias where appropriate, or rewrite only column references bound to that relation.
- Respect explicit aliases, nested scopes, quoted identifiers, and shadowed CTE names.
- Do not use global string replacement.

**Required tests:** Qualified parent references, explicit aliases, nested CTEs, mixed-case quoted names, and multiple scopes using the same name.

## 4. Restored transformation-agent calls bypass fast-path safety controls

**Severity: deployment blocker. Reproduced using the real client path with mocked HTTP responses.**

**Location:** `services/sttm-builder/app/core/sttm_builder.py:1616–1630`

The ZIP removes fast-path metadata and invokes the transformation specialist through ordinary `self.invoke()`.

That routes the request through the legacy client rather than the durable fast runtime. Consequently, the specialist does not share the fast runtime’s admission, call accounting, strict completion handling, and uncertainty safeguards.

The offline probe demonstrated:

- A timed-out POST was retried.
- A subsequent response marked `in_progress`, containing a tool-result block, yielded text that was accepted as a mapping.

**Impact:**

- Duplicate remote work after an ambiguous timeout.
- Model calls outside the intended fast-path accounting.
- Acceptance of output that has not met the fast path’s terminal-response requirements.

**Recommended change:**

Restoring the specialist is reasonable, but it must use an appropriately generalized version of the guarded runtime:

- Shared durable admission and call accounting.
- Request/thread correlation and archives.
- Strict terminal-response validation.
- No blind retry after an ambiguous remote outcome.
- Uncertain calls remain occupied/quarantined under the existing policy.

Do not restore the specialist merely by stripping the fast-path flags.

## 5. The specialist can run beyond the Auto-map deadline

**Severity: deployment blocker for the latency objective. Reproduced offline.**

**Location:** `services/sttm-builder/app/core/sttm_builder.py:1624–1644`

The ZIP checks the deadline before invoking the specialist, but does not pass the remaining time to the HTTP operation or reject late responses afterward.

The probes observed:

- A **240-second client timeout with only 10 seconds remaining**.
- Acceptance of a rule returned **90 seconds after the deadline**.

**Recommended change:**

- Use one shared deadline across preparation, source mapping, specialist calls, repairs, and finalization.
- Bound each call by the remaining time, reserving time for validation and persistence.
- Recheck the deadline after the response and before accepting results.
- Do not start repairs when insufficient time remains.
- Do not assume cancelling a local thread cancels remote model execution; preserve uncertainty handling.

**Required test:** Expire the deadline during both the initial specialist call and repair. Already validated mappings must survive, but late results must not be silently accepted.

## 6. Failed repair discards rules that already succeeded

**Severity: partial-result correctness defect. Reproduced offline.**

**Location:** `services/sttm-builder/app/core/sttm_builder.py:1631–1663`

Suppose the specialist returns:

```text
Target A: valid rule
Target B: missing rule
```

The system repairs B. If that repair fails, the exception handler rebuilds the result from the original source mappings and loses A’s valid rule.

**Recommended change:**

- Maintain validated rules per target outside the repair block.
- Merge valid initial rules before attempting repair.
- Repair only missing or invalid targets.
- If repair fails, retain A and mark only B unresolved.

**Required test:** A mixed response followed by a repair timeout must preserve the successful target exactly.

## 7. Specialist evidence IDs are merged without equivalent grounding checks

**Severity: evidence-integrity defect. Reproduced offline.**

**Location:** `services/sttm-builder/app/core/sttm_builder.py:1699–1715`

The specialist’s learning, inference, and recommendation IDs are unioned into the final mapping. The probe accepted invented IDs alongside a valid expression.

Valid SQL does not establish valid citations.

**Recommended change:**

- Check specialist citations against the target’s admitted evidence.
- Reject unsupported or other-target citations.
- Validate the merged expression, source bindings, dependencies, values, and evidence together before accepting the final mapping.
- Reuse the established grounding rules rather than implementing a weaker specialist-only check.

**Required test:** A syntactically valid expression with fabricated or unrelated evidence IDs must not pass as grounded.

## 8. Non-fast Auto-map handling regresses

**Severity: compatibility defect. Reproduced offline.**

**Location:** `services/sttm-builder/app/core/automap_batch.py:700–717`

Unresolved answers now enter a temporary `unresolved_response` dictionary for every mode, but that dictionary is consumed only in the fast branch.

The baseline finished with one call and retained the explicit no-match explanation. The ZIP made a second call and replaced that explanation with a repeated-decision error.

**Recommended change:**

- Keep the changed handling scoped to fast mode, or explicitly finalize the temporary results in every supported mode.
- Preserve valid unresolved decisions and their appropriate coverage explanations.
- Do not retry a completed no-match merely because it was stored in the wrong collection.

**Required test:** Run the same mixed mapped/unresolved response through legacy, parallel, and fast paths.

## 9. `suggested_queries` handling is useful but needs reconciliation

**Location:** `services/sttm-builder/app/core/automap_scan_transport.py:826–837`

The ZIP correctly treats suggestions as metadata rather than executable instructions or mapping JSON.

However, it differs from the unpublished local fix:

- ZIP permits **32 suggestions per block**, without an aggregate count across blocks.
- It rejects empty strings and strings over **2,048 characters**.
- Those extra string restrictions can discard otherwise valid mapping text; we have not established that the provider contract requires them.
- It lacks some of the unpublished fix’s safe response-shape diagnostics and integration coverage.

**Recommended change:**

- Reconcile the implementations deliberately; do not blindly overlay either file.
- Apply an aggregate bound and the existing response-byte limit.
- Preserve strict terminal status, answer-text, malformed-block, and tool-block checks.
- Keep suggestions inert and out of mapping interpretation.
- Record only safe shape/count diagnostics.

This fix alone does not solve the specialist bypass described above.

## 10. The acceptance evidence is still incomplete

The review run reported **946 passed, 10 failed, and 4 errors**. The remaining failures/errors in that run were caused by rejection of the real Ft. Pitt CTE definitions. Separate probes exposed additional defects that the supplied tests did not catch.

The synthetic 600-column tests passing is useful, but it does **not** establish that the actual pending-target request now fits and produces correct mappings.

Before deployment, I recommend these gates:

1. **Real upload compatibility:** Existing Ft. Pitt parsing, CTE handling, and preservation tests pass.
2. **Contract integrity:** Changed SQL, stale hashes, hidden columns, and invalid bindings are rejected.
3. **Transport safety:** Both agents obey admission, deadlines, completion checks, and uncertainty rules.
4. **Partial-result preservation:** One failed target or repair cannot erase successful targets.
5. **Actual packet sizing:** Measure the complete serialized request from the production-shaped fixture—not just an isolated source contract.
6. **Functional acceptance:** Verify an explicitly defined expected mapping and legitimate unresolved controls.
7. **Live UAT acceptance:** Only then measure correct results and click-to-result latency.

### One correction to my earlier 2803 conclusion

`BILLINGCOUNTRY ← COUNTRY_CODE` was the intended diagnostic mapping, and it exists in an authored mapping fixture. But that authored workflow includes an account-country lookup relationship.

**That does not, by itself, prove that a standalone country reference table is a valid household population source.** Source eligibility also does not prove target suitability. The archived “no eligible sources” explanation contradicted the packet, but zero mappings alone is not sufficient proof that a business-correct mapping was available.

For a reliable positive control, explicitly establish diagnostic identity intent—or provide the household-driving source and lookup relationship. Do not force a mapping merely to make the count nonzero.

## Recommended implementation order

1. Fix CTE wrapper recognition, hash validation, and scope-aware rebinding.
2. Put specialist calls behind guarded admission, completion, and deadline handling.
3. Preserve partial rules and validate specialist evidence.
4. Restore non-fast unresolved behavior.
5. Reconcile suggestion parsing and add missing regression tests.
6. Prove the actual packet and expected outcomes before deploying.

**Keep the narrow CTE-output-contract design. Fix how it is established and enforced; do not revert to sending every upstream column, and do not weaken validation just to obtain mappings.**
