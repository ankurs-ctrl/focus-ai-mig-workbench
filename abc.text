Yes — now that OAuth is created, your next steps are basically:

1. update `client.env`
2. rerun bootstrap for metadata/agents
3. deploy/upgrade SPCS app + Auto-map worker
4. confirm OAuth callback URL
5. smoke test login, session, agent, automap

Also: `AGT_SOURCE_MAPPING` not showing tools is expected. That agent is a specialist mapping LLM agent and currently has no own tools. The tool wiring is:

`AGT_STTM_BUILDER` → procedure tool `SP_SUBAGT_SOURCE_MAPPING` → calls `AGT_SOURCE_MAPPING`

And the Auto-map worker calls `AGT_SOURCE_MAPPING` directly.

So if you inspect `AGT_SOURCE_MAPPING` in Snowsight and see no tools, that alone is not a problem.

## Step 1 — Update `client.env`

Open:

```powershell
.\infra\snowflake\env\client.env
```

Make sure these are correct:

```env
AUTH_MODE=custom_oauth
SPCS_EXECUTE_AS_CALLER_ENABLED=true
SPCS_ENABLE_CUSTOM_CREDENTIALS=true

SNOWFLAKE_OAUTH_CLIENT_SECRET_OBJECT=FFP_HDP_OPS_DB_DEV.SCH_HDP_ADMIN.STTM_BUILDER_OAUTH_CLIENT_CREDENTIALS
SNOWFLAKE_OAUTH_SESSION_SECRET_OBJECT=FFP_HDP_OPS_DB_DEV.SCH_HDP_ADMIN.STTM_BUILDER_OAUTH_SESSION_KEYS

SNOWFLAKE_OAUTH_AUTHORIZE_URL=https://<client_account>.snowflakecomputing.com/oauth/authorize
SNOWFLAKE_OAUTH_TOKEN_URL=https://<client_account>.snowflakecomputing.com/oauth/token-request
SNOWFLAKE_OAUTH_REDIRECT_URI=https://<client_spcs_app_host>/api/v1/auth/callback
SNOWFLAKE_OAUTH_SCOPE=session:role-any
```

Important: since IT created the secrets in `FFP_HDP_OPS_DB_DEV.SCH_HDP_ADMIN`, use those fully-qualified secret names exactly.

Also make sure:

```env
SNOWFLAKE_STTM_BUILDER_AGENT=<APP_DB>.<APP_SCHEMA>.AGT_STTM_BUILDER
SNOWFLAKE_SOURCE_MAPPING_AGENT=<APP_DB>.<APP_SCHEMA>.AGT_SOURCE_MAPPING
```

And if you want the split Auto-map service:

```env
AUTO_MAPPING_COMPUTE_POOL=<existing_or_new_pool>
AUTO_MAPPING_SERVICE_NAME=<automap_service_name>
```

You can use the same compute pool as the app, but I’d prefer a separate Auto-map compute pool if the client allows it.

## Step 2 — Re-run metadata + agent bootstrap

Run this from repo root:

```powershell
.\scripts\bootstrap_sttm_metadata_infra.ps1 -EnvFile ".\infra\snowflake\env\client.env"
```

This updates:

- metadata tables
- helper procedures
- `AGT_SOURCE_MAPPING`
- `AGT_TRANSFORMATION_RULE`
- `AGT_STTM_BUILDER`
- dbt/test agents
- RAG-related metadata

It should not update `AGT_SEMANTIC_MODEL_V2`.

Do not run:

```powershell
.\scripts\rebind_semantic_model_v2_registry.py
```

unless you intentionally want to modify V2 binding.

## Step 3 — Confirm agent wiring

In Snowsight, check:

```sql
SHOW AGENTS LIKE 'AGT_STTM_BUILDER' IN SCHEMA <APP_DB>.<APP_SCHEMA>;
SHOW AGENTS LIKE 'AGT_SOURCE_MAPPING' IN SCHEMA <APP_DB>.<APP_SCHEMA>;
SHOW PROCEDURES LIKE 'SP_SUBAGT_SOURCE_MAPPING' IN SCHEMA <APP_DB>.<APP_SCHEMA>;
SHOW PROCEDURES LIKE 'SP_SUBAGT_TRANSFORMATION_RULE' IN SCHEMA <APP_DB>.<APP_SCHEMA>;
```

Expected:

- `AGT_STTM_BUILDER` should show tools:
  - `SearchWorkbenchRag`
  - `AGT_SOURCE_MAPPING`
  - `AGT_TRANSFORMATION_RULE`

- `AGT_SOURCE_MAPPING` may show no tools. That is okay.

## Step 4 — Deploy SPCS app + Auto-map worker

Run:

```powershell
.\scripts\deploy_spcs_client_snow.ps1 -EnvFile ".\infra\snowflake\env\client.env"
```

This script handles both:

- main web app service
- separate Auto-map worker service

It builds and pushes:

- `sttm-builder`
- `sttm-automap-worker`
- `frontend`
- `nginx`

Then it creates/upgrades:

- `WEBAPP_SERVICE_NAME`
- `AUTO_MAPPING_SERVICE_NAME`

If images are already pushed and you only want to re-render/redeploy specs:

```powershell
.\scripts\deploy_spcs_client_snow.ps1 -EnvFile ".\infra\snowflake\env\client.env" -SkipBuild
```

## Step 5 — Confirm OAuth redirect URL

After deployment, get the public endpoint from:

```powershell
snow spcs service list-endpoints <WEBAPP_SERVICE_NAME> `
  -c <SNOWFLAKE_CONNECTION> `
  --database <APP_DB> `
  --schema <APP_SCHEMA>
```

Your OAuth redirect URI must exactly be:

```text
https://<public_service_host>/api/v1/auth/callback
```

If the host is different from what IT used while creating OAuth, ask IT to update the security integration redirect URI.

## Step 6 — Smoke test

Open the public SPCS app URL.

Test in order:

1. Login with Snowflake.
2. Confirm `/api/v1/auth/session` returns signed-in user.
3. Select source/target tables.
4. Ask assistant “hello”.
5. Ask table/context question.
6. Try derived-source generation.
7. Go to mapping page.
8. Click Auto.
9. Check Auto-map worker logs if Auto-map stalls.

For logs:

```powershell
snow spcs service logs <WEBAPP_SERVICE_NAME> `
  -c <SNOWFLAKE_CONNECTION> `
  --database <APP_DB> `
  --schema <APP_SCHEMA>
```

And:

```powershell
snow spcs service logs <AUTO_MAPPING_SERVICE_NAME> `
  -c <SNOWFLAKE_CONNECTION> `
  --database <APP_DB> `
  --schema <APP_SCHEMA>
```

## Key answer on Auto-map tools

No, `AGT_SOURCE_MAPPING` itself does not need tools added.

It works like this:

```text
Auto button
  → Main backend
  → Auto-map worker service
  → AGT_SOURCE_MAPPING
  → structured mappings returned to UI
```

For chat/manual orchestration:

```text
AI Assistant
  → AGT_STTM_BUILDER
  → SP_SUBAGT_SOURCE_MAPPING
  → AGT_SOURCE_MAPPING
```

So the place where tools matter is mostly `AGT_STTM_BUILDER`, not `AGT_SOURCE_MAPPING`.
