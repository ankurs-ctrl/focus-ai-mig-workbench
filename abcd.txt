## Why it passed before and fails now

Both runs were on mapping 2002, an hour apart. I compared the two saved requests field by field. Everything is the same size except the workspace state:

| Request field | Passed (07:37) | Failed (08:57) |
|---|---|---|
| Semantic context | 382,995 | 382,995 |
| Relation graph | about 69,700 | about 69,700 |
| Selected columns | 17,330 | 17,330 |
| Target attributes | 14,078 | 14,078 |
| Execution context | 3,670 | 3,670 |
| Workspace state | 168,053 | 267,555 |

The 99,502-character difference sits in four workspace fields, which were empty in the first run:

| Workspace field | Added characters | What it holds |
|---|---|---|
| `compiled_mapping_context_hash` | 74,247 | A string starting `{"compilerContractVersion"…`. It is the full serialized compiler input, not a hash. |
| `auto_map_outcome` | 8,537 | Proposals saved from the previous Auto-map run |
| `compiled_mapping_sql` | 6,908 | Compiled mapping SQL |
| `compiled_mapping_preview_sql` | 6,042 | Preview SQL |

After the scan code strips what it already carries elsewhere, the workspace left in every message grows from about 22,000 to about 118,000 characters. It is about 22,000 again if those four fields are removed.

The code that builds this message (`automap_scan_context.py:373-377`) removes only some workspace keys and keeps the rest, including those four. Every scan message therefore includes them. Mapping rows were not the difference.

The chat assistant already handles these fields correctly. `assistant_retrieval.py:54-65` moves them out of the message and notes "legacy clients put serialized compiler inputs here, not a digest". The Auto-map scan path never got that treatment.

## Why this bites now

The workspace state depends on what you did in the UI. A fresh mapping has these fields empty and passes. After the SQL is compiled or a previous Auto-map has run, they fill up and the same mapping fails. This is also why mapping 2601 failed earlier: the first fix removed repeated table semantics, but this workspace data still crowds the budget. That is my reading; I haven't proven it.
