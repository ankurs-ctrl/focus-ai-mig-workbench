Safe, Cost-Controlled Workbench Performance Plan
Summary
Optimize the application without changing mapping logic, semantic evidence, FIR recommendations, prompts, confidence rules, or generated outputs.

The CoCo analysis identifies useful bottlenecks, but four recommendations require adjustment:

Do not move all workloads to Medium; metadata, autosave, preview, and routine queries remain on XS.
Do not scale the web application while Auto-Mapping shares its compute pool.
Do not delete the legacy relationship fallback globally; skip it only where cached metadata proves it cannot return anything.
Do not parallelize Snowflake operations through one shared session or use non-durable background jobs.
Medium usage will be benchmark-gated because no preference was provided: each heavy workload moves only if it delivers at least 30% better p95 latency within the agreed credit budget.

Implementation Plan
1. Establish performance evidence
Add query tags and stage timings for selection, relationship discovery, semantic preparation, FIR retrieval, Auto-Mapping, autosave, agent context preparation, DBT, and test generation.
Return Server-Timing diagnostics in non-production or admin-enabled requests.
Record cache status, session creation/reuse, warehouse, credits, queued time, agent time-to-first-token, total response time, and output size.
Benchmark fixed cold and warm scenarios before changing behavior.
Confirm that the CoCo sidecar receives no traffic before removing it.
2. Apply low-risk application optimizations
Remove the unused CoCo sidecar after the zero-traffic check, releasing CPU and memory without changing STTM AI behavior.
Keep one webapp instance while Auto-Mapping uses the shared pool.
Set the user Snowflake-session cache TTL to 1,800 seconds.
Reuse sessions by user token, role, workload, warehouse, database, and schema.
Do not add periodic SELECT 1 health checks. Evict and recreate a session once only after a real expiration or connection error.
Fix prepared-context durable-cache writes to use bound JSON parameters instead of SQL string interpolation.
Log and measure durable-cache persistence failures instead of silently treating them as ordinary cache misses.
3. Parallelize context preparation safely
Add a bounded Snowflake session-lease pool:
Maximum four parallel operations per request.
Maximum twelve active leases per webapp instance.
One separate Snowpark session per concurrent worker.
Thirty-minute idle TTL with lazy creation.
Sequential fallback if leases are unavailable.
In FIR learning retrieval, resolve project/link scope first and then concurrently fetch independent evidence sources such as prior mappings, semantic learnings, corrections, curated versions, precedents, and FIR recommendations.
Run semantic-bundle preparation and learning retrieval concurrently using separate sessions.
Merge results in a stable deterministic order.
Preserve every existing evidence item, recommendation, confidence value, provenance ID, and prompt input.
Use context hashes to prove that sequential and parallel preparation produce equivalent packages.
4. Eliminate unnecessary relationship calls
Continue reading raw semantic-view relationships first.
Preserve existing confidence and relationship-qualification rules.
Call the legacy relationship procedure only when:
Semantic evidence did not provide a relationship; and
Cached schema capability indicates that foreign-key or legacy relationship evidence may exist.
Cache negative capability results by database/schema and metadata version so schemas with no foreign keys do not repeatedly execute an empty procedure.
Keep the old behavior behind a rollback flag for environments where the procedure is useful.
5. Make autosave fast and durable
Keep core mapping persistence synchronous:
Workspace snapshot.
Selected sources and target.
Mapping rows and hardcoded values.
Relationships and derived-source references.
STTM header/version update.
Retain the existing frontend debounce and add strict payload-hash deduplication and single-flight behavior so an unchanged workspace does not write again.
Move non-authoritative projections—agent artifacts, FIR feedback events, learning projections, feature snapshots, and target-pattern updates—to durable post-save jobs.
Add an idempotent TBL_WORKBENCH_ASYNC_JOBS table with job type, snapshot ID, idempotency key, status, lease, attempts, next-attempt time, and error details.
Let backend instances claim and process jobs with bounded retries. A restart must resume pending or expired jobs.
If job enqueueing fails, run the projection inline so data is never lost.
Publishing must wait for or drain the current snapshot’s projection job; normal autosave need not wait.
Extend the autosave response backward-compatibly with projection job ID and status.
6. Improve streaming and UI responsiveness
Buffer agent token deltas and update the UI at most every 50 milliseconds or once per animation frame.
Flush immediately on completion, status changes, errors, cancellation, and unmount.
Memoize completed messages so only the active streaming response is reparsed.
Preserve the exact final text, markdown, SQL blocks, citations, and token order.
Do not truncate agent responses, reduce evidence, downgrade models, or shorten reasoning prompts.
7. Optimize FIR and semantic queries from measured profiles
First verify how frequently SP_FIR_GET_AGENT_RECOMMENDATIONS actually runs. It should normally be served through prepared-context and learning caches rather than execute on every chat turn.
Inspect query-operator statistics for cold executions.
Push project, target, trigger, context, and status filters ahead of FLATTEN, joins, and ranking operations.
Cache the final FIR recommendation package by context hash, target identity, semantic version, and learning-evidence epoch.
Invalidate it when relevant semantic versions, approved learnings, mappings, or corrections change.
Add clustering or search optimization only when query profiles show selective scans that justify the recurring credit cost.
8. Separate compute workloads
Move Auto-Mapping to the requested dedicated CPU_X64_S compute pool:
Minimum one node.
Maximum two nodes initially.
One worker normally, scaling to two only under queue pressure.
Auto-suspend when idle.
Keep the webapp on its existing compute pool.
After separation, load-test the webapp with the CoCo sidecar removed.
Scale the webapp to two instances only if CPU remains above 70% or request-queue p95 remains above one second under representative concurrency.
Do not rely on local process memory for authoritative state because multiple instances may be introduced later.
9. Use warehouses by workload and evidence
Add a PREPARATION workload route without changing existing API contracts:

CONTROL: XS for metadata, registries, autosave, project state, and small repeated queries.
AUTOMAP: XS warehouse; performance isolation comes primarily from the dedicated compute pool.
EXECUTION: XS for SQL validation and normal previews.
PREPARATION: candidate for Medium for cold semantic composition and FIR learning preparation.
AGENT: independently benchmark Medium for interactive agent preparation and Cortex calls.
Medium policy:

Single cluster initially, with approximately 60-second auto-suspend.
No multi-cluster configuration unless measured queueing remains after code parallelization.
Enable Medium independently for PREPARATION and AGENT only when that route improves p95 latency by at least 30%.
Retain Medium only when credits per successful fixed-workload run remain within 10% of the approved baseline or an explicitly accepted performance premium.
If an agent call is dominated by Cortex service time and Medium provides no meaningful gain, keep it on XS.
Never route autosave, metadata navigation, cache lookups, or routine repeated queries to Medium.
Interfaces and Deployment
Add optional workload value PREPARATION to warehouse routing.
Add backward-compatible autosave fields for post_save_job_id and post_save_status.
Add feature flags for parallel learning, parallel preparation, relationship fallback skipping, asynchronous post-save projection, stream batching, and Medium workload routing.
Apply idempotent DDL for the asynchronous job table and cache-supporting objects.
Runtime code must use pre-created objects and must not attempt privileged DDL.
Optional caller-grant statements must remain non-blocking and disabled where deployment roles lack MANAGE GRANTS.
Do not require Snowflake tasks; backend workers process durable jobs.
Verification and Rollout
Capture the unchanged baseline.
Deploy instrumentation, JSON binding, session TTL, and CoCo removal.
Enable relationship-call skipping and frontend stream batching.
Enable parallel FIR retrieval in shadow mode and compare context hashes.
Enable parallel semantic/learning preparation.
Enable durable asynchronous post-save processing.
Move Auto-Mapping to its dedicated pool.
Benchmark Medium separately for PREPARATION and AGENT.
Enable each Medium route only after its performance-and-credit gate passes.
Consider webapp instance scaling only after compute-pool separation.
Acceptance requirements:

No regression in mapping counts, column lineage, hardcoded values, relationships, derived sources, semantic evidence, recommendation schemas, evidence IDs, confidence, or generated SQL.
Parallel and sequential context packages are semantically equivalent and deterministically ordered.
No lost autosaves or projection jobs during process restarts, session expiration, or transient Snowflake failures.
Cold prepared-context latency improves by at least 50%.
Warm prepared-context p95 is below one second where cache data is valid.
Ordinary autosave acknowledgement p95 is below three seconds; projections complete within thirty seconds p95.
Agent time-to-first-token improves by at least 40% on the fixed test corpus without response-quality regression.
No token loss or markdown corruption during long streamed responses.
Credits per fixed end-to-end scenario do not increase by more than 10% unless a separately approved Medium performance premium applies.
Every optimization can be disabled independently without rolling back unrelated fixes.
Assumptions
The current AI response quality, evidence coverage, and recommendation behavior are the reference contract.
Medium routing is benchmark-gated rather than enabled globally.
The Auto-Mapping pool will be provisioned separately, but code optimizations can be deployed before it becomes available.
Webapp scaling remains deferred while the pool is shared.
Existing raw semantic-view confidence rules remain unchanged.
