So the new patch did its job. We’re past the token problem. Now it’s an agent authorization / active-role problem.
What this usually means:
The SPCS session is running under a different Snowflake role than the one you granted on the agent.
Or that role has USAGE on the DB/schema, but not USAGE ON AGENT.
Or the user’s DEFAULT_ROLE is different, and Snowflake is evaluating the agent call with that role.
Please check these exactly in client Snowflake:
SHOW GRANTS ON AGENT FFP_HDP_DLAB_DB_DEV.SCH_STTM_METADATA.AGT_STTM_BUILDER;
SHOW GRANTS TO ROLE FFP_HDP_DLAB_DB_DEPLOY_ROLE_DEV;
Make sure this role has all three:
GRANT USAGE ON DATABASE FFP_HDP_DLAB_DB_DEV TO ROLE FFP_HDP_DLAB_DB_DEPLOY_ROLE_DEV;
GRANT USAGE ON SCHEMA FFP_HDP_DLAB_DB_DEV.SCH_STTM_METADATA TO ROLE FFP_HDP_DLAB_DB_DEPLOY_ROLE_DEV;
GRANT USAGE ON AGENT FFP_HDP_DLAB_DB_DEV.SCH_STTM_METADATA.AGT_STTM_BUILDER TO ROLE FFP_HDP_DLAB_DB_DEPLOY_ROLE_DEV;
Do the same for the other agents too:
AGT_SOURCE_MAPPING
AGT_WORKBENCH_CONVERSATION
AGT_SEMANTIC_MODEL
AGT_DBT_CONVERSION
Then verify the user’s default role:
DESC USER ANKURSINHA;
If DEFAULT_ROLE is not FFP_HDP_DLAB_DB_DEPLOY_ROLE_DEV, set it:
ALTER USER ANKURSINHA SET DEFAULT_ROLE = FFP_HDP_DLAB_DB_DEPLOY_ROLE_DEV;
Why this changed:
Before, the app was failing earlier on the bad token path.
After the fix, it now uses the Snowflake session token correctly, so Snowflake is finally checking the real runtime role against the actual agent object. That’s why you now see “agent does not exist or not authorized for the current role.”
So short version: this is most likely not a code bug anymore. It’s the active role used by the SPCS session not matching the role granted on the agent.
