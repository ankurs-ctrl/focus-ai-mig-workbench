## Plan

**Phase 1: fix verified losses on the current path (no agent change)**
- **Canonical target key:** one function implementing Snowflake identifier rules (unquoted resolves case-insensitively, quoted preserved, ambiguity rejected). Use it in scope validation, preservation and result application, and keep display names unchanged. Tests: `BillingCity`, `BILLINGCITY`, `"BillingCity"`, and an ambiguous pair.
- **Per-target checkpoint table:** unique on `(job_id, target_key, input_revision)`, with status `accepted | review | unresolved | not_completed` and a payload reference. Write it right after validation, before FIR or artifact work, using an idempotent merge. After a deadline, mark remaining targets `not_completed` and finish the parent as partial success. The UI reads this table, not the parent's final result.
- **Phase timing and per-stage timeouts** from the stages in prompt B, written as structured logs to an event table or tracing.

**Phase 2: fix context on the current path**
- **Evidence ledger:** one record per `(target, evidence_id, content_hash, input_revision)` with states proposed, requested, returned, admitted, cited. Pin evidence for unresolved candidates, and generate repair feedback from the ledger so it can't contradict admission state.
- **Delta follow-ups:** send only the active target's candidates, deficits and new evidence. Replace the 77 KB key-candidate block with a summary and an on-demand read.
- **Acceptance:** the BILLINGCITY transcript replays cleanly, and a one-target follow-up is a small fraction of the initial packet.

This gives you a measured baseline, and you may find the 8-round chains shrink without any agent change.

**Phase 3: native tool prove-out (decision point: depends on prompt A)**
- Spike three tools only (`SearchSources`, `ReadEvidence`, `ValidateProposal`) plus a `SubmitProposals` that validates internally.
- Proceed only if the agent beats the phase 2 baseline on time and tool calls per target at equal or better accuracy, with no scope or access escapes.
- If custom tools aren't supported, keep the loop but batch `evidence_requests` and resolve them from the ledger.

**Phase 4: quality and extras**
- Structured `semantic_fit` (exact, approximate, proxy, mismatch) with a review lane for proxy or mismatch. Defer Analyst until the core tools are proven.
- **Gold-set eval:** a small test set from your approved mappings (question 1), scored per target, with business-implausible auto-selections required to be zero.
