## 1. An expired upload worker can overwrite a newer worker’s verified results

### Affected code

- `services/sttm-builder/app/routers/upload.py:938–947`
- `services/sttm-builder/app/core/fir_asset_resolver.py:74–87`
- `services/sttm-builder/app/core/sql_upload_jobs.py:86–109`

### What is wrong

There are two different identities:

- `PROCESSING_ID`: identifies the logical processing run.
- `GENERATION` and `LEASE_TOKEN`: identify the worker attempt currently allowed to update that run.

When a lease expires and another worker takes over, the generation/token changes, but the logical `PROCESSING_ID` remains the same.

The worker passes this stable identifier into background processing:

```python
processing_generation=row['PROCESSING_ID']
```

Reference persistence then replaces rows for that processing ID:

```python
BEGIN TRANSACTION
DELETE ... WHERE asset_id = ? AND project_id = ? AND verification_generation = ?
# Persist replacement references
COMMIT
```

**That transaction does not verify that the worker still owns the current lease.**

The final request-status update does check generation, token, and lease expiry—but that happens after the reference writes.

### Reproduced failure

1. Worker A begins verification.
2. Worker A pauses; its lease expires.
3. Worker B claims the request with a newer generation.
4. Worker B saves verified references and marks processing complete.
5. Worker A resumes and replaces those references with `lookup_failed`.
6. Worker A’s final status update is rejected as stale.

The resulting state is contradictory:

```text
Request:    completed / reference_enrichment=ready
References: catalog_status=lookup_failed
            semantic_status=lookup_failed
```

### Why it matters

The final status fence gives the appearance of protection, but stale work can already have damaged the underlying evidence.

### Required correction

Fence **every authoritative publication**, not only the final status row.

A suitable design must ensure that:

- Publication uses the expected request, caller, role, generation, and lease token.
- Ownership validation and reference publication cannot race with takeover.
- If ownership is lost, no reference replacement commits.
- Other background side effects are reviewed for the same problem.

Two possible implementations are:

- A transactionally serialized ownership check plus publication.
- Attempt-specific immutable results, followed by a fenced update selecting the authoritative result.

A standalone “check lease, then write” is insufficient: the lease could change between those operations.

### Required regression

Pause A, let B take over and complete, then resume A. Assert that:

- B’s references remain unchanged.
- A cannot publish references or status.
- Request status and reference status remain consistent.

This needs a test of the **background side effects**, not just `SqlUploadJobs.save()`.

## 2. Reference lookup can select another caller’s processing snapshot

### Affected code

`services/sttm-builder/app/routers/upload.py:1375–1405`

### What is wrong

When `upload_request_id` is supplied, the endpoint resolves the request through the caller-scoped job lookup.

Without it, the fallback selects the newest processing record using only the asset and project:

```sql
WHERE RESULT_PAYLOAD:asset_id::STRING = ?
  AND PROJECT_ID = ?
  AND REQUEST_PAYLOAD:reuse_request_id IS NULL
ORDER BY CREATED_AT DESC
LIMIT 1
```

It does not constrain that selection by:

- Requesting user.
- Requesting role.
- Relevant upload options/content identity.

It then uses the selected `PROCESSING_ID` to retrieve references.

### Reproduced failure

- Alice uploads an asset in a project.
- Bob uploads the same asset in that project with a newer processing record.
- Alice requests references without `upload_request_id`.
- The fallback selects Bob’s processing snapshot.

This was reproduced through the actual route with simulated SQL results.

**This establishes wrong-snapshot selection. It does not establish a live privilege escalation or actual cross-user data exposure.**

### Required correction

For durable uploads:

- Require the exact upload request identity.
- Resolve it through the existing authorized job lookup.
- Verify its result belongs to the requested asset and project.
- Use only that request’s processing snapshot.

For legacy requests without an ID:

- Implement an explicitly scoped, unambiguous fallback.
- Do not choose an arbitrary “latest” record across callers.
- Return a recoverable ambiguity/unavailable response when the correct snapshot cannot be established.

Do not weaken the backend’s caller isolation to make recovery easier.

### Required regressions

- Same asset/project uploaded by two users.
- Same user switching roles.
- Same file with different upload options.
- Multiple generations for one request.
- Legacy lookup with multiple possible matches.

Each caller must receive only the correct processing snapshot—or a clear refusal to guess.

## 3. The actual Contacts upload still cannot compile completely

### Affected code

- `frontend/src/features/sttm/mapping/sql-upload-workspace.ts:296–318`
- `frontend/src/app/sttm/builder/new/mapping/page.tsx:832–845`
- `services/sttm-builder/app/core/mapping_sql.py:437–451`
- `services/sttm-builder/app/core/mapping_sql.py:893–899`

### What now works

The repeated-table improvement is real:

- Four CTEs survive.
- Seven outer LEFT joins survive.
- `ccMail`, `ccOther`, `scMail`, and `scOther` remain distinct.
- Apply and snapshot/reopen preserve those instances.
- The lookup-only projection subset compiles.

But **46 of 49 individual mapping rows compile; three fail**. Full compilation stops at the first failure.

### 3A. Quoted target identifiers lose their SQL identity

Failing targets:

```text
Import Notes
IndvAccount.FinServ__Status__c
```

These are authored as quoted output aliases:

```sql
AS "Import Notes"
AS "IndvAccount.FinServ__Status__c"
```

The workspace extracts a bare string:

```typescript
const targetColumn = String(
  item.target_alias ?? item.target_field ?? item.target_column
);
```

The compiler later receives that string without the necessary identifier representation and reports:

```text
Invalid target column
```

The dot in `"IndvAccount.FinServ__Status__c"` is part of **one quoted identifier**, not a qualification separator.

### Required correction

Preserve the distinction between:

- Display label.
- Canonical target identity.
- SQL identifier representation.

Use a quote-aware representation and render identifiers safely at the compiler boundary. Do not:

- Strip spaces or dots.
- Rename the targets automatically.
- Treat a literal dot inside quotes as a separator.
- Simply relax identifier validation.

### 3B. `HEADOFHOUSEHOLD` remains an unbound dependency

Failing target:

```text
xxxIndv_ACCOUNT_FinServ__SourceSystemID__c
```

Compiler error:

```text
Undefined relation or alias in dependency: HEADOFHOUSEHOLD
```

The authored expression uses:

```sql
CASE HEADOFHOUSEHOLD ...
```

The workspace qualifies bare source columns only when there is one outer relation:

```typescript
if (!rewritten.includes(".") && singleRelationAlias) {
  return `${singleRelationAlias}.${rewritten}`;
}
```

Contacts has multiple outer relations, so the bare dependency remains unresolved.

### Required correction

Resolve unqualified columns using the parsed query scope and each relation’s available output columns.

- If exactly one visible relation supplies the column, bind it to that relation instance.
- For a CTE, use its output contract—not hidden parent-table columns.
- If multiple relations supply it, report ambiguity.
- Preserve consistency between the expression and its dependency bindings.

Do not arbitrarily attach all bare columns to the driving relation.

### Required regressions

Run the **exact Contacts file** through:

```text
Parse → Apply → graph construction → save/reopen → full compilation
```

Assert that:

- All 49 individual rows compile.
- The full mapping compiles.
- Both quoted target aliases remain exact.
- `HEADOFHOUSEHOLD` resolves to the correct visible CTE output.
- Ambiguous bare-column cases are rejected rather than guessed.

## 4. Quoted physical-table names are incorrectly treated as equal

### Affected code

`frontend/src/features/sttm/shared/sttm-selection-utils.ts:67–71`

### What is wrong

The new instance-suppression logic uppercases the complete physical name:

```typescript
table.qualifiedName.toUpperCase()
```

It uses that value to suppress physical selections already represented by imported relation instances.

However, these Snowflake names are distinct:

```sql
D.S."Country"
D.S."COUNTRY"
```

Uppercasing both strings destroys the distinction.

### Reproduced failure

Input:

- Two imported instances of `D.S."Country"`.
- A separate selected physical table `D.S."COUNTRY"`.

Output:

- Only the two imported instances remain.
- The distinct selected table is incorrectly removed.

### Required correction

Use one quote-aware canonical identifier function:

- Normalize unquoted components according to Snowflake rules.
- Preserve quoted component case and escaped quotes.
- Distinguish physical identity from relation-instance identity.
- Use the same comparison rules throughout selection and graph hydration.

Do not uppercase the whole FQN or split identifiers naively on dots.

### Required regressions

Cover:

- Unquoted case variants that should match.
- Quoted case variants that must remain distinct.
- Quoted names containing dots.
- Escaped double quotes.
- Multiple instances of one physical table plus another distinct table.
- Save/reopen and metadata refresh preserving those selections.

## 5. Upload recovery loses its browser handle too early and across caller changes

This contains two related defects.

### 5A. Completed previews lose recovery before Apply

**Affected code:** `frontend/src/features/dashboard/NewMappingDialog.tsx:349–374`

The response is placed into React state, then its persistent recovery handle is deleted:

```typescript
if (['completed', 'failed'].includes(receipt.status)) clearHandle();
```

### Reproduced failure

1. Upload finishes.
2. The preview is displayed.
3. User reloads before Apply.
4. React state disappears.
5. The persistent request handle is already gone.
6. `checkSavedUpload()` returns without fetching the saved preview.

The server result still exists; the frontend has discarded its recovery path.

### Required correction

Separate:

- Processing finished.
- Preview available.
- Preview applied or explicitly discarded.

Retain recoverability until Apply succeeds or the user explicitly dismisses the pending import. A failed background-enrichment result that still contains a useful preview also needs a deliberate retention policy.

### Required regression

Complete upload, reload before Apply, recover the same preview without another POST. Then Apply successfully and retire the handle at the appropriate point.

### 5B. Recovery keys omit caller and role

**Affected code:** `frontend/src/features/sttm/mapping/sql-upload-recovery.ts:5–6`

Current key:

```typescript
sql-upload-recovery:v1:<project>:<mapping-or-new>
```

It does not identify the authenticated account/user/role.

### Reproduced failure

1. Alice leaves a saved request handle.
2. Another user or role uses the same browser/project.
3. Backend authorization correctly returns 404 for that request.
4. Repeated 404s become `not_accepted`.
5. The frontend deletes Alice’s handle.

This is **recovery-state loss**, not a failure of backend authorization.

### Required correction

- Namespace handles by the authenticated account/user/role and project/mapping.
- Wait for identity to be resolved before attempting recovery.
- Do not delete one identity’s handle while another identity is active.
- Treat “not visible to this caller” separately from confidently establishing nonacceptance.

No credentials or tokens should be stored in the recovery key.

### Required regressions

Test user switches, role switches, logout/login, shared project use, and returning to the original identity. The original authorized caller must retain its recovery path.

## 6. Reference polling can hang indefinitely despite having an attempt limit

### Affected code

`frontend/src/features/sttm/mapping/sql-bundle-review-panel.tsx:301–338`

### What is wrong

The effect first awaits a request-status GET:

```typescript
await fetch(statusUrl, { signal: controller.signal });
```

Then it fetches references.

Both use an AbortController that is cancelled on effect cleanup, but neither has an elapsed-time timeout.

The retry timer is scheduled **after** the awaited requests finish:

```typescript
if (attempts < 20) timer = setTimeout(refresh, 1500);
```

Therefore, twenty attempts do not bound the total wait. If the first request never settles, attempt one can last indefinitely.

### Reproduced failure

With the status GET held pending:

- No reference GET occurs.
- No next-attempt timer is scheduled.
- No exhaustion warning appears.
- The panel waits until cleanup.

The separate `observeSqlUpload()` helper already has bounded observation, but this panel bypasses it.

### Required correction

- Apply a per-request timeout and an overall observation deadline.
- Distinguish timeout from component-unmount cancellation.
- Preserve initial verified results during failures.
- Show a recoverable status after the observation budget ends.
- Handle authentication/status errors explicitly.
- Cancel obsolete requests when the upload request identity changes.
- Review the effect dependencies: it currently depends on project and asset, not `upload_request_id`.

That final dependency issue follows from code inspection; it was not separately reproduced in the earlier probe.

### Required regressions

- Status GET never resolves.
- Reference GET never resolves.
- Repeated server errors.
- Authentication expires.
- Component unmounts.
- A new processing request replaces the old one for the same asset.

The panel must terminate observation predictably and must not replace newer state with an obsolete response.
