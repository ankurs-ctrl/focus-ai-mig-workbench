1. WHAT OUR TOOL DOES

Our application helps users build source-to-target data migration mappings in Snowflake.

Users can:
- Select source tables and a target table.
- Define a driving source, joins, filters, and business rules.
- Upload existing SQL containing CTEs, transformations, constants, and population logic.
- Inspect and edit target-column mappings.
- Generate and validate mapping SQL.
- Review AI-generated mapping proposals, alternatives, confidence, and explanations.
- Reuse applicable semantic knowledge, prior mappings, and learned rules.

The frontend is Next.js/React with Redux state management. The backend is Python, using Snowflake and Snowpark. The application and Auto-map workers run in Snowpark Container Services.

Auto-map proposes mapping definitions. Running Auto-map does not itself authorize publication or loading data into target tables.

2. OUR AUTOMAP AGENTS

The two relevant deployed Cortex Agents are:

AGT_SOURCE_MAPPING
- Interprets target-column meaning.
- Selects plausible source bindings.
- Identifies dependencies and candidate alternatives.
- Explains confidence and uncertainty.
- Identifies when transformation logic or more evidence is needed.
- Returns structured per-target mapping proposals.

AGT_TRANSFORMATION_RULE
- Receives selected source bindings, target requirements, and focused evidence.
- Generates SQL transformation expressions where direct mapping is insufficient.
- Returns rules that the backend validates for source scope, project Values, and compilation.

The backend also performs discovery, exact evidence retrieval, orchestration, validation, and persistence. These are application functions, not necessarily separate autonomous agents.

Calling a Cortex Agent endpoint does not mean the current workflow is fully tool-driven. The current implementation largely uses application-managed reasoning rounds. The model can request evidence using a structured meta.evidence_requests protocol; the backend validates and executes those requests before another model call.

Do not assume native tools are configured or unavailable without inspecting the actual agent specification and API capabilities.

3. WHAT AUTOMAP MUST DO

The intended UI has one Auto-map button:
- No target checkboxes selected: process all targets.
- Some targets selected: process exactly those targets, across pagination.
- Existing definitions must remain intact while replacement proposals await explicit acceptance.
- Unresolved results must never erase working mappings.
- Newer manual edits must take precedence over older AI responses.

Auto-map must work for:
- Fresh manually constructed mappings.
- SQL uploads with authored mappings and CTEs.
- Repeated runs after sources, joins, SQL, filters, or project Values change.
- Selected-target completion and reevaluation.
- Existing-target reevaluation without silent overwriting.

For SQL uploads, retain original SQL separately from normalized compiler representations. Preserve joins, filters, constants, quoting, alias identity, and population semantics.

A selected CTE exposes its verified output columns. Its parent tables and SQL remain available to the backend for lineage and validation, but parent columns must not automatically become selectable outer sources. CTEs do not automatically become one native Snowflake Semantic View each.

6. HOW THE MODEL CONTEXT IS BUILT

The application freezes a canonical context, then creates bounded model packets containing:
- Requested targets.
- Mandatory context.
- Selected source and target evidence.
- Exact-read results.
- An explicit selectable_sources roster.
- Evidence-graph references.
- Coverage and unresolved issues.
- Response instructions/schema examples.

The implementation uses lossless factoring and dictionary/object-shape references to reduce repeated content. Large evidence may be represented by hashed blocks with offsets and ownership/purpose metadata.

The model must not treat a source’s presence in the complete archive or graph index as permission to select it. The active packet and verified binding/evidence contract govern the decision.

7. WHAT THE EVIDENCE GRAPH WAS INTENDED TO DO

The intended graph is for agent-led investigation:

- Discover relevant candidate bindings and evidence.
- Inspect source/CTE dependencies and join relationships.
- Request exact missing semantics or rules.
- Read additional evidence only when necessary.
- Compare alternatives and make a supported mapping decision.

The backend should enforce scope, access, identity, budgets, and correctness—not dictate every investigation step.

The current implementation only partly achieves this. It supports structured evidence requests, but automatic backend selection and pagination still control much of the context.

Evidence existing in the graph, being requested, being returned, and being sufficient for a decision are distinct states.

8. CURRENT EXECUTION AND SAFETY MODEL

The deployed environment has:
- Five Auto-map worker instances.
- Four shared durable model-call permits.
- Durable parent jobs with target batches.
- Shared deadlines and call accounting.
- Scoped immutable request/response archives.
- Lease/fencing and uncertain-outcome quarantine.

Source decisions, evidence reviews, and specialist calls share bounded runtime resources.

The backend deterministically checks:
- Response structure.
- Source identity and graph accessibility.
- Admitted evidence and citations.
- Expression and Value validity.
- SQL binding/compilation.
- Target scope.
- Preservation and revision safety.

These protections must remain. They should not be confused with deterministic business mapping.
