## Architecture
**1. What it is.** It's a Cortex Agent with tools. The LLM is set to `auto`, so no specific model is pinned. It has a 900-second and 400K-token limit per run. It uses no Cortex Analyst or Cortex Search, only 4 custom stored-procedure tools, all written in Python:
- `generate_test_cases` runs `GENERATE_AND_RUN_TEST_CASES`. It checks curated-layer tables for schema, primary/foreign/alternate keys, NOT NULL, blanks and duplicates.
- `run_lineage_tests` runs `RUN_LINEAGE_TESTS`. It traces lineage from Snowflake's `ACCESS_HISTORY` and `OBJECT_DEPENDENCIES` views and finds orphan tables and columns.
- `generate_lineage_diagram` draws a lineage diagram as a PNG and as text.
- `validate_raw_layer` checks raw-layer tables in 7 areas: data quality, duplicates across batches, soft deletes, finding the matching curated table, raw-to-curated lineage, and transformation rules (DIRECT, UPPER, TRIM, COALESCE, LOOKUP, CONCAT).

None of the procedures call Cortex or AI_COMPLETE. The LLM picks the tool and formats the results; it doesn't write the tests.

**2. Mapping documents.** Mappings are read from a Snowflake table (`LINEAGE_STTM_MAPPING`, 11 columns including TRANSFORM_RULE) that has to be loaded first. The agent doesn't parse Excel files itself. That table is currently empty. The structured mapping data lives in `SCH_STTM_METADATA.TBL_STTM*` (329 mappings, 5,795 attributes, 39 versions, last updated 27 Oct). Separate agents fill those tables (AGT_STTM_BUILDER, AGT_SOURCE_MAPPING, AGT_TRANSFORMATION_RULE). Your team should confirm how the Excel files get into them.

**3. Data access.**
- The procedures run on the warehouse `FFP_HDP_DLAB_DB_ADHOC_XS_WH_DEV`, with a 600-second query timeout.
- Raw query results such as counts and failing values go into the output, so the LLM does see results. Whether it sees full rows is something I'd need to read the procedure code to confirm.
- No procedure has an external access integration, so nothing leaves Snowflake through the tools. The LLM itself runs inside Cortex.
- I didn't check the execution role (owner's or caller's rights). Everything is owned by `FFP_HDP_DLAB_DB_DEPLOY_ROLE_DEV`, which isn't a read-only role.

**4. Azure DevOps.** There's no direct connection. The output is a 10-column table in Azure DevOps test-case import format (ID, Work Item Type, Title, Test Step, Step Action, Step Expected, Area Path, Assigned To, State, Test Status). It's saved to a results table and downloaded as a CSV, and someone then imports it into Azure DevOps by hand. Please say "exports to Azure DevOps import format", not "publishes".

## How it works
**5. Templates or AI-generated?** Rule-based. The checks are fixed by type in Python and filled in from the table's metadata and mappings. "From templates" is the accurate wording. "AI-generated" overstates it; "AI-orchestrated" fits.

**6. Review points.** Nothing in the system enforces a review. New test cases get the state "Design". Engineers see the results table with PASSED / FAILED / WARNING / INFO, and WARNING and INFO mean "needs manual review". The diagram can show review at the results/CSV step and again at import into Azure DevOps.

**7. Environments.** Everything is in `*_DEV` (dev database, warehouse and role). I found no sign of QA, UAT or production in this account.
